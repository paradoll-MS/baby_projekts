# 一、核心概念与理念主干 

## 1. 客户需求与调香层级体系 (0.0 — 3.0 整体分层定理)

**【结论】** 切分轴首先是对**客户香气需求层次**的划分，不同层次的需求再对应不同的调香工作内容。该体系从理论分类上自下而上展开，但在真实客户 Brief 处理中通常是自上而下串联执行。

### 1.0 层：感官表现力 — 分子与韵/味的关系

**核心命题**：什么样的分子及其组合会形成什么样的感官体验（sensation）；又怎样通过调整分子使该感官体验达到目标。

**子任务（四个基本问题）**：

| 编号 | 子任务 | 核心问题 | 适用场景 |
|------|--------|----------|----------|
| 1.1 | **像** | 与目标气味有多像？ | 仿香：有明确 Benchmark，需要达到化学组成与感官表现的双重接近 |
| 1.2 | **好** | 配方本身是否平衡、协调、自然？ | 所有封闭型任务；拆分为**平衡**、**协调**、**细致**三个独立维度 |
| 1.3 | **强** | 整体或特定方向的感官表现是否足够？ | 需要在特定香韵或整体感知上增强表现力，同时不破坏结构 |
| 1.4 | **便宜** | 在保持"像、好、强"的条件下能否更便宜？ | 给定价格 cap，在约束内最大化感官表现 |

**1.0 的核心关系**：**分子 ↔ 韵/味（sensation）**。工作对象是相对明确的"味"，机器要把目标感官效果反推为分子选择、比例和结构调整。

*(演进与纠偏原因：1.2 最初被 AI 通过板书误读为"改"字，经用户纠正为"好"。同时 1.0 整体被确认为"分子与韵之间的关系"，即从物质构成到 sensation 的映射与优化，而非对香气身份本身的重新定义。)*

### 1.5 层：Fine Fragrance 向 Consumer Fragrance 的转换

**【结论】** 1.5 是广义 1.0 范畴内的特殊子层，专门处理已有 fine fragrance 香气资产向 consumer/functional fragrance 的调用与适配。其核心不是"创香"，而是**选型、调用和品类化落地**。

- **归属**：本质上仍属于 1.0（给定一个香型让它变得"更适合某个品类"）
- **不承担**：新的情感叙事、观念表达或创意创作（全部归入 2.0）
- **逻辑链路**：场景和人群需求识别 → 判断目标消费者认知与偏好 → 调用已有 fine fragrance 配方或香气结构 → 针对具体基质和使用条件改造 → 完成功能型香氛产品
- **典型产品**：沐浴露、柔顺剂、洗衣液、家清产品等

*(所有情感叙事和观念表达全部在 2.0 完成；functional fragrance 中不存在"创香"，只是对已有 fine fragrance 资产的调用和品类化应用改造。)*

### 2.0 层：用气味表达 — 韵/味与词的关系

**【结论】** 2.0 的核心不是"让香气更好"，而是**让气味能够表达、能够说话**。它将难以言传的主观嗅觉感受对象化为可描述、可交流的自然语言对象，再进一步连接到文化和语义联想。

**核心关系**：**韵/味 ↔ 词与语义**

**三个关键环节**：

1. **主观感受对象化**：将难以言传的 sensation 变为相对稳定的感官描述对象（如明亮、湿润、柔软、冷峻、透明、厚重、流动、断裂）
2. **对象语言化**：将感官对象组织成自然语言可描述和组合的词汇体系
3. **语言语义化**：利用词汇在文化语境中的关联，使气味能够表达情绪、场景、人格、意象或概念

**主要发生在**：Fine fragrance（personal fragrance 和 home fragrance），因为这类产品的核心用途就是被闻、被体验

**产品链路（自上而下）**：品牌主张、产品概念、目标用户 → 产品故事 → 香气故事（2.0）→ 在现有香精库中寻找合适配方 → 转换到具体品类（1.5）→ 对"好"和"便宜"等表现优化（1.0）→ 完成法规/稳定性校验（0.0）

*(1.0 与 2.0 的边界被精确表述为：1.0 是"分子与韵之间的关系"，2.0 是"韵与词之间的关系"。)*

### 0.0 层：产品成立的必要条件（硬约束与产品底座层）

**【结论】** 0.0 处理的是"这个配方在现实中能不能成为一个合格产品"，不涉及"香气表达什么"。它是所有上层工作的**底座和硬约束层**。

**五大子模块**：

| 编号 | 功能 | 处理内容 |
|------|------|----------|
| 0-01 | 法规诊断与修复 | IFRA、REACH、GHS、HALAL、MSDS 及不同国家/品类/客户的法规要求 |
| 0-02 | 稳定性诊断与优化 | 不同基质或应用体系中的稳定性测试、特殊物料风险和替代方案 |
| 0-03 | 一致性诊断与修复 | 原料来源、规格、浓度、储存、包装、工艺和批次差异 |
| 0-04 | 理化与应用适配 | VP、LogP、闪点、溶解性等理化参数与工艺适配 |
| 0-05 | 配方可行性校验 | 总量、剂量、可采购性、禁用料等基础检查 |

**执行原则**：这些模块主要依赖规则、数据库查询和确定性计算，**不可由大模型自行判断**。无论仿香、优化还是语义表达，最终必须回到这一层完成产品化验证。

**【硬约束 vs 软目标】** 系统中存在两类条件：

- **硬性条件（不可商量的必要条件）**：法规合规、稳定性、批次间一致性、明确的单价上限等 0.0 要求
- **软性目标（在硬约束内尽可能优化）**：尽可能像、尽可能好、尽可能强、尽可能匹配产品概念或香气故事

在必要条件必须满足的前提下，最大化指定的优化目标。同一任务可以在不同价格 cap（如无上限、100 元/kg、50 元/kg）下分别生成多个候选解。

### 3.0 层：开放式创香（本期排除边界）

**【结论】** 3.0 处理的是 fine fragrance/艺术香水中的开放式创作：初始目标只有一个大致方向，Version 0 不只是待优化的答案，也是新的创作刺激；人闻到结果后可能改变的不是配方参数，而是创作目标本身。气味、语言、联想和创作意图相互推动、共同演化，不存在一开始就完全确定的终点。

**排除理由**：3.0 的工作目标本身在过程中不断变化，需要人的自主创作与方向选择持续参与，不属于当前可自动化的封闭任务范围。**本期系统范围严格限定为 0.0—2.0 的相对封闭型任务。**

### 五层总览

| 层次 | 核心关系 | 核心问题 | 本期开工范围 |
|------|----------|----------|-------------|
| 0.0 | 产品与现实约束 | 能不能成为产品？ | 开工 |
| 1.0 | 分子 ↔ 韵/味 | 像不像？好不好？强不强？贵不贵？ | 开工 |
| 1.5 | 气味身份 ↔ 新品类语境 | 同一个气味怎样适配另一种产品？ | 开工 |
| 2.0 | 韵/味 ↔ 词与语义 | 这个气味在表达什么、让人联想到什么？ | 开工（C 类原型） |
| 3.0 | 气味 ↔ 创作意图持续互动 | 我在创作过程中究竟想表达什么？ | 本期排除 |

## 2. "料 — 韵/味 — 词 — 意" 的四级逻辑体系

**【结论】** "韵"（味 / Sensation）是整个系统最关键的**中枢映射夹层**，向上和向下分别关联两个抽象层级，形成不可断裂的完整认知链条：

```
料（分子结构 / 配方浓度 / 物料表现）
    ↕  ← 形而下（物理化学层）：物质构成决定感官
韵/味（Sensation = 主观感受到的气味）
    ↕  ← 中枢映射：对象化为可描述的感知单元
词（对象化感官词汇 / 自然语言描述）
    ↕  ← 形而上（语义文化层）：语言激活联想
意（文化语义 / 品牌主张 / 情绪 / 场景联想）
```

- **料 → 韵/味**（向下追溯）：韵可落实为具体的分子构成、配方浓度组成与物料表现——这是 1.0 层的工作域
- **韵/味 → 词**（向上对象化）：单个韵对象化为感知对象和语言对象；多个韵的组合（象形/情景）形成更完整的可自然语言描述的感官结构——这是 2.0 层的核心转译环节
- **词 → 意**（再向上抽象化）：特定词汇利用其在人类生活经验和文化语境中的关联，连接到品牌主张、情绪意象、场景叙事和观念表达

**关键推论**：
- 无论在单个韵的层面还是在情景组合（象形）层面，都可以进行对象化和语义化转译与联想
- 这是 2.0 层"用气味表达"功能的理论基础
- 计算逻辑必须锚定在"语言-感觉-物质结构"的语义-化学对应关系矩阵上

## 3. 四大原料角色与 OAV 数值模型

### OAV 定义与公式

**【结论】**

$$OAV = \frac{C}{T}$$

- **OAV**（Olfactory Activity Value）：嗅觉活性值，一个无量纲值，用于量化原料在配方中的感官贡献强度
- **C（Concentration）**：暂简化为配方中的占比（不在此阶段结合空间传质等复杂问题）
- **T（Threshold）**：感知阈值，即能够闻到该原料的最低浓度
- **有效区间**：OAV 值在 **3—10** 之间，原料才能在配方中起到可识别的作用

*(gpt老师最初提出了多个变量定义的不确定性——C 是配方浓度还是空气中浓度、T 是哪一种 odor threshold、OAV 是单料计算还是对整个香韵计算。乐总明确了第一阶段简化处理：C = 配方占比，T = 最低感知阈值，OAV 先按单一物料计算。)*

### 四大角色矩阵

**【结论】** 配方中的每种原料可根据其 OAV 值及浓度/阈值特征划分为四种角色。同一原料在不同用量下可扮演不同角色——**角色不是原料的固定标签，而是在某一个具体浓度和配方语境中的动态功能**。任何原料在具体配方中出现的感官有效作用窗口通常不会跨越四个数量级。

| 角色 | 英文 | C（浓度）特征 | T（阈值）特征 | OAV 表现规则 | 在配方中的实际贡献 | 操作规范 |
|------|------|-------------|-------------|-------------|-------------------|----------|
| **主料** | Performer | 用量浓度很高，在总配方中占极显著比例 | 极低或处于适中区间 | 呈现极高 OAV 数值 | 担当核心框架主力，直接决定特定"韵"的基本定义与主香型特质 | **不可轻易大幅削减**，其替换必将破坏骨架身份 |
| **辅料** | Mediator | 浓度比例次之，明显低于主料用量 | 一般处于正常或偏低区间 | OAV 数值显著小于主料，呈现适度贡献 | 补充和完善主结构特征，连接核心韵与辅韵形成整体构图；具较强跨配方适应性 | 决定结构间过渡衔接与香型丰满度 |
| **点缀** | Modifier | 占比极少，一般以痕量或极低比例添加 | 感知阈值极其低下（微微克级） | OAV 数值中等或稍高，但在微量下显极强活跃度 | 提供香气特征的个性细节与生动感；决定一个香韵呈现的是抽象样板还是具体生动的生命力（如红玫瑰 vs 白玫瑰） | 须在已有主料+辅料框架上精准匹配引入，避免乱加料造成气息散乱浑浊 |
| **和合** | Blender | 绝对添加比例通常很高（如大量麝香、定香基底料） | 嗅觉感知阈值比较高 | OAV 相对较小或处于基础作用区间 | 作为承载整体的底层背景画布，柔化消除高 OAV 原料间的冲突对比度，将不同断裂结构融合为均匀、柔和、圆滑的整体感觉 | 提供背景质感，决定最终画面的尖锐/柔和程度 |

# 二、业务功能分支：0.0 至 2.0 完整规格细节

## 1. 0.0 硬约束与产品底座层

**【结论】** 本层共包含五个独立且不可改变的原子物理规约模块，核心目标是确保香精配方能够成为一个**切实可制造、符合法规安全准入、能够在现实物理基质中长期稳定**的现实产品。这些约束作为系统求解过程中的硬边界（Hard Constraints），**凡触犯本层规则的配方方案，无论其感官如何优异，必须予以否决或修改**，不可用于任何软目标的平衡交换。

### 0-01 法规诊断与修复

- **输入**：配方版本 ID、目标销售地区（可多选，如 CN/EU/US）、加香目标消费品类、特定大客户采购限制标准
- **处理机制**：逐个校验配方物料中单一单体及复杂天然原料所挟带的限定化学成分是否符合 IFRA、REACH、GHS、HALAL、MSDS 以及地区专项规范；当识别到禁用物或浓度超标料时，锁定问题物料并自合规组分库匹配同功能替用组分
- **约束条件**：一律拒绝输出存在任一合规越线指标的候选配方
- **解决的痛点**：人工核对法规繁琐易错、多地区同步出口时因限用量复杂导致开发完成后因违规推回重造的设计浪费

### 0-02 稳定性诊断与优化

- **输入**：配方组分及用量、具体产品化学基质体系（如强酸清洁剂、高 pH 洗衣液、表面活性剂水溶液等）、最终加香浓度量
- **处理机制**：调取基质-原料加速反应与长周测试库，评估高风险基团（如醛类与胺或强氧化强酸体系反应、易致变色沉淀料）稳定性概率；对具有突变降解、分层或变色风险物料做出调低比重或换用高稳定衍生物的处理
- **约束条件**：稳定性不通过则不可放行
- **解决的痛点**：避免配方出样经过长周温变和光照老化实验出现严重变色降解或香气丧失、避免由于未提前预估基质冲突导致反复回炉

### 0-03 一致性诊断与修复

- **输入**：配方、原料规格和供应商信息、批次记录
- **处理机制**：在发生原辅料供应商变更、原料产地或生产工艺规格调换以及单批次波动的情况下，通过对比标准理化与质谱检测数据，修复因微量异变成分引入所引发的感官气味漂移和品质不均
- **约束条件**：批次间感官一致性必须保证
- **解决的痛点**：解决供应链原材料多源切换及批次偏差引起的产品气味波动、解决凭经验凭运气调整代用品导致配方感官走样的痛点

### 0-04 理化与应用适配

- **输入**：配方、目标应用体系参数（溶解性要求、闪点限制、工艺温度等）
- **处理机制**：根据物料的蒸汽压（VP）、油水分配系数（LogP）、闪点及在基质当中的直接溶解度进行评估。筛查香气进入载体体系后能否均匀分散、避免生产加工高热挥发损失以及闪点安全合规
- **约束条件**：适配不通过则标记为不可生产
- **解决的痛点**：解决选取的香料在基质里浮油不溶或产品灌装制造工艺中极易快速逸散的问题

### 0-05 配方可行性校验

- **输入**：任意候选配方
- **处理机制**：做最终的制造可落地计算——保证完整公式配方总量严格等于 100%、处理多级稀释浓度溶液折算、实现各系统或实验室习惯质量/体积计量单位转换、验证全配方选料是否属于有效现货库存且单笔采购限制没有断货风险
- **约束条件**：任一可行性检查不通过则阻塞
- **解决的痛点**：消除实验室草稿配方由于单位折算失误、基数不等于一百或由于采用了已停产无法批量采购物料所导致的后续死锁

## 2. 1.0 感官表现力层

### 2.1 1.1 "像"（仿香）

**核心链路**：Benchmark → GC-MS → 识别/推测成分及复配油 → 校正因子 → Version 0 → 反打验证（Version 0 再次 GC-MS 与 Benchmark 谱图对比 → 校正因子校准）→ 迭代优化

**关键概念——反打（Reverse GC-MS Verification）**：
- **定义**：将依 Benchmark 谱图生成的 Version 0 配方实物再次注入 GC-MS，获得其实际谱图，与 Benchmark 原始谱图对比
- **目的**：验证校正因子的准确性；若两个谱图存在偏差，说明校正因子需要调整——这是一种校准机制
- **优化双目标**：以"**谱图指标最大相似度 + 关键主料 OAV 特征最大一致性**"为双目标不断自迭代至及格相似表现

**模块分解**：

#### 1-01 Benchmark 重构
- **输入**：Benchmark 的 GC-MS 谱图、已知成分、复配油信息、历史仿香案例
- **处理机制**：谱图算法 → 成分识别与复配油推测 → 校正因子应用 → 初始仿香 Version 0 生成
- **AI 角色**：推测未知峰可能的复配油来源；检索历史仿香案例；总结差异
- **不适于 AI**：裸算峰面积、校正因子和浓度（GC-MS/谱图算法负责）

#### 1-02 相似度诊断
- **输入**：当前配方 + Benchmark
- **处理机制**：从化学组成和感官表现两个角度对比
- **多维相似度输出**（不可只是一项总分）：关键香韵一致性、Performer 一致性、香气结构比例一致性、缺失或多余特征、价格约束下可保留的相似度
- **计算引擎**：特征工程 + 距离函数 + 机器学习排序

#### 1-03 相似度优化
- **输入**：当前配方、Benchmark、硬约束（法规、稳定性、价格 cap）
- **处理机制**：约束优化——在硬约束内最大化相似度
- **输出**：不同价格 cap 下的多个候选解，每个显示相似度指标与成本、感官变化

### 2.2 1.2 "好"（结构优异性）

**【结论】** "好"不是一个笼统的主观判断，而是可拆分为三个独立技术维度：**平衡**、**协调（Pairing）**、**细致（分形/自相似）**。三者分别对应不同的评价策略和优化算法。

#### 1-04 平衡诊断与优化

**定义**：同一个配方中，不同原料和不同韵的显著程度是否处在合适的感官位置。

**诊断依据**：
- 每种原料的 OAV
- Performer/Mediator/Modifier/Blender 的角色分布是否合理
- 是否存在 overdose（某个香韵过度压制其他结构）
- 角色配置是否与历史成功配方的统计范围相符

**优化机制**：基于成功配方学习正常 OAV 范围与角色分布模式 → 定位异常 → 提出调整建议 → 生成候选改方

#### 1-05 协调诊断与优化（Pairing）

**【结论】** 协调是韵与韵之间的 pairing 关系：两个韵是否适合搭配。

**底层机理**：
- 决定韵与韵是否搭配的主要因素是**各韵中高 OAV 的 Performer 之间是否搭配**（因为 Performer 决定了这个韵"是什么"）
- 较低 OAV 的 Mediator 或 Modifier 通常具有更强的跨配方适应性，不是决定协调关系的主要因素
- 因此，"两个韵搭不搭"这一主观感官问题，可转化为"高 OAV 主料之间的共现关系"这一可计算问题


**计算机制**：
- 从几万条历史配方数据中提取每种原料的共现频率
- 计算条件概率、PMI 或其他关联指标
- **关键**：必须在控制香型、角色、数量级和应用品类后计算关联强度（否则极常用原料会虚假地与所有原料高度相关）
- 区分成功配方与失败配方中的共现差异
- 识别 Version 0 到成交配方的共同增减模式

**输出**：协调评分（韵对韵）、问题定位（哪些 Performer 组合属于低频或高风险搭配）、改善连接的 Mediator/Blender 建议、候选改方

#### 1-06 细致度诊断与优化（分形/自相似）

**【终局结论】** 细致指的是香气整体展现出如同自然界形式美学中的"分形（Fractal）与自相似性"——当配方具有多个数量级的细节层次时，令香韵不是由抽象干瘪的主组分构成，而是具有丰沛的层次和极其生动的自然感。

**层次模型（以玫瑰为例）**：
1. **仅 Performer**：框架上是玫瑰，但只是粗糙抽象的样板，闻起来抽象、不自然、没有灵性
2. **+ Mediator**：结构更完整，完成主韵和辅韵的整体构图
3. **+ Modifier**：增加具体生动的细节——白玫瑰 vs 红玫瑰、鲜活 vs 干瘪（决定"生命感"）
4. **+ Blender**：调整整体画面的质感——尖锐高对比 vs 柔和融合

*(值得一提：引入"分形"概念解释自然感——自然界的形式美感具有自相似性，在调香中也存在同样现象。仅依靠 Performer 及少量 Mediator 虽然能搭出一个合格的特征骨架，但那只是粗糙抽象的样板。且香精物料在具体配方中出现的感官有效作用窗口通常不会跨越四个数量级，同一物料处在不同数量级范围时其代表的感官特征及担纲角色完全不同。)*

**数据基础设施**：
- 每种原料必须按照其常用出现的**三到四个数量级**分别标注：
  - 在该数量级下呈现什么香型
  - 在配方里通常扮演什么角色（同一原料在不同数量级下可能是 Performer、Mediator 或 Modifier）
  - 通常与哪些 Performer、Mediator 或 Modifier 组合
- 必须预建"不同原料在 3-4 个数量级下各自对应的香型与配方角色词典"

**优化机制**：
- 诊断配方是否只有 Performer、缺乏 Mediator 和 Modifier
- 基于历史案例检索 + 候选排序 + 图学习模型，在给定 Performer 和 Mediator 构成的框架上，**精准匹配**适当数量级的 Modifier 进行精细细节补全
- 引入合适 Blender 完成层级过渡
- 检查增加细节后是否变得杂乱或失衡
- **核心警告**：绝不能乱加料——必须在已有主辅结构基础上计算匹配，否则会造成气息散乱浑浊

---

### 2.3 1.3 "强"

**核心原则**："强"绝不能简单等于增加总剂量或乘系数放大总加香剂量——此做法极易越过感知最大窗口引爆局部过载（Overdose），并引发稳定性沉淀与合规超限。正确做法是：优化器综合读取原料最低阈值 $T$、蒸汽压 VP 释放参数与具体载体中各料释放效率评价，识别哪些香气特征单元有提升余量，**选择性提高对强度具极高放大贡献率的物料的 OAV**。

| 编号 | 模块 | 输入 | 处理机制 | 输出 |
|------|------|------|----------|------|
| 1-07 | 整体强度诊断与优化 | 配方 + 强度目标 | 分析 OAV 分布，定位可提升的原料，避免 overdose | 强度诊断 + 整体增强候选配方 |
| 1-08 | 指定香韵增强 | 配方 + 目标香韵 | 聚焦指定韵的 Performer/Mediator，提高强度同时保护其他结构 | 针对性增强方案 |
| 1-09 | 表现曲线优化 | 配方 + VP/LogP/扩散数据 | 结合挥发、扩散和留香信息，调整不同时间阶段的表现 | 时间曲线调整方案 |

**技术路线**：主体为预测模型 + 约束优化。AI 可学习哪些调整真正提升感知强度（vs 仅增加用量造成 overdose），并负责理解"增强整体"还是"增强某个韵"以及解释修改方案。

---

### 2.4 1.4 "便宜"

**核心原则**：在法规、稳定性和价格上限必须满足的前提下，最大化相似度、平衡度或其他指定目标。这不是按比例缩减成本，而是在维持表现的情况下重构。关键在于核算**物料成本效率比**（即其贡献的具体 OAV 强度与该原料单位成本一公斤进货价的数学比值），优先将效率极低的物料直接删降。

**模块 1-10：成本诊断与约束优化**

- **输入**：配方、价格 cap（可多个档位，如无限制 / 100 元/kg / 50 元/kg）、硬约束
- **处理机制**：
  - 核算每个物料的 OAV/价格 比（"感官贡献效率"指标），优先将效率极低的物料删降
  - 针对同一功能角色、同一韵群或等效感官贡献结构的物料，在无感官降级前提下匹配便宜的替代单体或成熟低价复合底基（Base）
  - 在每个香气方向/结构簇内做降本，而非均匀削减
  - 替换后重新平衡
  - 在法规、稳定性和最低感官质量线下，通过约束优化器（线性/非线性/整数规划）求解
  - **关键约束**：执行完成后必将配方自动再输入至 1.2 平衡检查模块做结构平衡调整
- **输出**：不同价格 cap 下的多个候选方案（如无限制、100 元/kg、50 元/kg 梯度），每个显示成本与感官损失对比

**AI 角色**：帮助寻找候选替代物和总结历史降本经验。但成本计算与最终求解**必须由优化器完成**——这是最不需要大模型的模块之一。

## 3. 1.5 跨场景转换层

**【结论】** 1.5 层专为把个人高级香水与高端环境香薰等高级香氛（Fine Fragrance）的经典成型香型配方资产，迁移和改造成适合应用于各种洗涤、清洁、护理等功能型或大众消费品（Functional Fragrance / Consumer Products）的特定场景转化层。本质上仍属于广义 1.0 范畴，是 1.0 和 2.0 之间的过渡层（夹层）。

**转换的核心操作逻辑**：
1. 从香精库匹配 Fine Fragrance → 
2. **精炼并保留原配方 60%—80% 决定其特质身份的主框架及主料** → 
3. 彻底剔除或精简掉 20%—40% 对普通基质容易引发挥发过度或表现混乱的多余极其复杂精微装饰表达 → 
4. 留出必要的结构间隙并使用底基作平滑衔接平衡 → 
5. 全量接受 0.0 底座的强酸/强碱稳定性、高性价比成本上线以及地区严控法规安全校验



| 编号 | 模块 | 输入 | 处理机制 |
|------|------|------|----------|
| 1.5-01 | Brief 与香精库匹配 | Brief、品类、场景、目标人群 | 语义检索 + 大模型：将客户非标准香型语言转译 → 在现有香精库中匹配合适配方 |
| 1.5-02 | 香气身份提取 | 选中的 fine fragrance 配方 | 分析哪些 Performer/香韵/结构是不可丢失的身份要素（60%-80% 保留率判断） |
| 1.5-03 | Consumer 转换 | 原配方 + 目标品类参数 | 案例学习 + 品类知识 + 约束优化：去繁就简、留出层次间隔 |
| 1.5-04 | 品类适配优化 | 转换后配方 + 品类约束 | 结合基质、剂量、成本、稳定性和品类偏好完成最终改方 → 回 0.0 全量校验 |

**技术定位**：典型的**混合模块**——大模型选择方向和匹配语义，专业算法完成落地。

## 4. 2.0 用气味表达层

**【终局结论】** 2.0 在整套系统里最依赖大模型，但最后的"感官结构 → Version 0"仍不能只靠大模型，必须调用香韵-分子知识、历史配方检索以及 1.0 三个模块（平衡、协调、细致）和 0.0 硬约束模块。

| 编号 | 模块 | 输入 | 主要任务 | AI 必要程度 |
|------|------|------|----------|------------|
| 2-01 | 品牌与产品概念解析 | 客户 Brief（自然语言） | 提取品牌主张、产品概念、目标用户、表达目的 | **必须** |
| 2-02 | 产品故事生成与结构化 | 概念解析结果 | 将散乱 Brief 整理成完整、可操作的产品故事 | **必须** |
| 2-03 | 产品故事到香气故事 | 产品故事 | 把产品语义转换成气味能够表达的叙事 | **必须** |
| 2-04 | 香气故事到感官结构 | 香气故事 | 生成香韵、场景、感官词汇和三调表 | **必须** |
| 2-05 | 感官结构到 Version 0 | 三调表 + 感官词汇 | 将语言对象和香韵结构转成分子和组合 | 高度必要（但须结合专业算法） |
| 2-06 | 概念匹配诊断与优化 | 已有配方 + 产品概念 | 判断配方表达的语义是否吻合品牌/产品概念，进行改方 | **必须** |

**关键约束**：2-05（感官结构 → Version 0）不能只靠大模型凭语言自由生成配方，必须再调用：香韵-分子知识库、历史配方检索、平衡模块（1-04）、协调模块（1-05）、细致模块（1-06）、硬约束模块（0.0 全系列）。

## 5. Version 0 获取的三条路径

Version 0 是系统所有优化工作的起点。大多数功能模块的标准入口是：**现成配方（Version 0）＋明确目标与约束 → 诊断、优化并生成新配方**。获取 Version 0 有三条路径：

### 路径 A：仿香路径
Benchmark / GC-MS → 成分分析 → 校正因子 → 初始仿香 Version 0

### 路径 B：1.5 路径（香精库匹配）
Brief（品类、目标人群） → 匹配现有 fine fragrance 配方 → Consumer fragrance Version 0

### 路径 C：2.0 路径（语义生成）
品牌主张/产品概念 → 产品故事 → 香气故事 → 香气描述和三调表 → 分子与组合 → Version 0

**关键要求**：无论走哪条路径，Version 0 的生成都不能只完成"词、韵与分子"的对应，还必须在生成过程中嵌入 1.2"好"的要求（平衡、协调、细致），使初始配方本身就达到"八九不离十"的状态。

# 三、系统架构与算法底座分支

## 1. 总体设计原则

**【结论】** 为避免简单使用"裸的大语言模型 API 直接一次性吐出完整精确化学配方表"的极高幻觉失准风险，整个系统不应被设计成"一个大模型直接生成配方"，而应将所有决策与算力做**三层彻底分离**：

```
+-------------------------------------------------------------------------------+
|                    任务编排与自然语言处理层 (LLM / Agent)                        |
|  职责：解析非结构化 Brief / 提取硬约束与软指标 / 规划模块调用序列 /                  |
|        对调香师的自然语言反馈进行转译 / 对结果做出文字化解释                          |
+-------------------------------------------------------------------------------+
                                       |
                                       v
+-------------------------------------------------------------------------------+
|                    统计优调与图学习引擎层 (专业算法模块)                            |
```

## 3. 共享算法底座（X-01 至 X-07）

### X-01：配方标准化引擎

统一处理：原料名称和编码、浓度和稀释液、配方总量、复配油与单体区分、单位换算、同一物料的不同供应商规格。

### X-02：OAV 与角色引擎

**输入**：一张标准化配方
**输出**：每种原料的浓度、感知阈值、OAV、当前数量级、当前香型、当前角色（Performer/Mediator/Modifier/Blender）、对哪些香韵产生主要贡献

这是平衡、协调、细致、强度和降本模块的共同基础。

### X-03：香韵结构引擎

**输入**：一张配方（原料清单）
**输出**：主要香韵、次要香韵、各香韵的 Performer/Mediator/Modifier/Blender、香韵之间的比例和关系、可语言化的感官描述

### X-04：原料关系图谱

基于几万条历史配方计算：
- 原料共现频率、条件概率、PMI 或其他关联指标
- **在控制香型、角色、数量级和应用品类后的关联强度**（关键：防止极常用原料虚假高度相关）
- Performer 之间的搭配权重
- Performer/Mediator 与 Modifier 的关联
- 原料替换和共同增减规律
- 成功配方 vs 失败配方中的共现差异
- Version 0 到成交配方的共同增减模式

### X-05：历史案例检索引擎

**检索对象**：完整的修改轨迹（Version 0 → 诊断 → 修改动作 → 新版本 → 人的反馈 → 最终客户结果），而非仅最终配方。

**检索维度**：香型、目标任务、应用品类、原料结构、硬约束、感官问题描述、成功改法。

**技术实现**：向量数据库 + 语义检索，将企业知识存入向量库，在回答和生成时动态调取。

### X-06：约束与优化引擎

处理三类条件：

1. **硬约束**：法规、稳定性、成本 cap、禁限用原料、应用剂量——必须满足
2. **质量保护线**：本轮优化虽然不是为了"像"，但相似度不能降到某水平以下；虽在降本，但平衡不能明显恶化
3. **主要优化目标**：本轮真正需要最大化或最小化的指标

支持在不同价格 cap 下同时输出多组方案（如：无 cap 最佳方案、100 元/kg 方案、80 元/kg 方案、50 元/kg 方案）。

### X-07：解释与追溯引擎

每个候选配方必须输出：为什么做这个修改、使用了哪条规则或哪个历史案例、哪些原料角色发生了变化、哪个指标改善、哪些方面可能退化、结果的可信程度。

## 4. 标准模块输入/输出协议 (Input/Output Contract)

所有业务模块采用统一的"模块合同"。

### 标准输入

```json
{
```

## 5. 人机互调与学习反馈闭环

### 数据流

1. 中台创建智能调香任务
2. 将项目、Brief、配方版本和任务要求发送给 Formulation Intelligence Service
3. 智能服务从受控接口读取原料和配方数据
4. 智能服务运行诊断和优化
5. 候选配方返回中台的"实验区"
6. **调香师选择、调整或拒绝候选——只有调香师确认后，新配方才进入正式配方库**
7. 打样、试香、测试和客户结果回写学习系统

### 核心原则

> AI 可以生成候选配方，但不能绕过人直接覆盖正式配方。

### 一条完整学习案例的结构

- 原始 Brief
- Version 0
- 本轮任务和优化目的
- 硬约束
- 系统诊断与候选配方
- 调香师选择了哪个方案、实际做了什么修改
- 感官反馈（支持自然语言输入，如"玫瑰框架对了但太粉、没有鲜活感、尾部略闷"）
- 稳定性和其他测试结果
- 客户反馈：是否寄样、确认、成交
- 最终生产配方

### 自然语言反馈的结构化

大模型将调香师的自然语言反馈预结构化为：
- 目标香韵
- 正向部分（已达标的）
- 具体问题（分条列出）
- 保护条件（不得改变的部分）
- 建议调用模块

**结构化结果必须由调香师一键确认或修改后，才进入正式学习数据。**

### 学习数据的筛选分级——五级准入验证漏斗

**【结论】** 不能把调香师每一次点击都当作正确答案，也不能每收到一句反馈就自动训练模型。真正高价值的训练案例必须依次通过五级验证准入：

```
+-----------------------------------------------------------------------------------------+
|                                调香师 / 内部人员 / 客户                                    |
|              (非结构化语言反馈 / 打样测试数据 / 嗅觉评价 / 寄样结果 / 销售确单结果)              |
+-----------------------------------------------------------------------------------------+
      |                                       |
      | 【日常行为操作流】(直接记录)               | 【实质反馈内容】(自然语言语义翻译)
      v                                       v
+-----------------------------+       +---------------------------------------------------+
|     事件日志系统 (不直进模型)  |       |        LLM 编排解析：语言到结构化任务转化模块          |
| 记录：展开对比/剔除候选/局部改动 |       | 翻译结果：[肯定项] / [问题指标] / [限定禁指方向]       |
+-----------------------------+       +---------------------------------------------------+
                                              |
                                              | (经专业调香师界面一键复查并签字确认)
                                              v
                                     +---------------------------------------------------+
                                     |            五大层级安全阈值准入验证漏斗              |
                                     | 1) 专业感官评价成立  2) 理化稳定性通过  3) GC-MS反打闭环  |
                                     | 4) 客户寄样正式通过  5) 完成商业投款交易投产              |
                                     +---------------------------------------------------+
                                              |
                                              | (满足并准入高质量标准训练集)
                                              v
                                     +---------------------------------------------------+
                                     |             专属向量案例记忆库与经验卡片             |
                                     |    持久化沉淀：Version(n) -> 结构化依据 -> 终态方案    |
                                     +---------------------------------------------------+
```

**五级准入标准（从低到高）**：

| 级别 | 信号类型 | 准入条件 | 训练权重 |
|------|----------|----------|----------|
| **L1** | 行为信号 | 调香师查看了哪些候选、选择了哪个、拒绝了哪些、对数值的手动调整 | **不入训练集**，仅入行为日志 |
| **L2** | 专业确认 | 具备专业认证身份的调香师判定出样确认达标或存在明确表现好坏评价 | 低权重 |
| **L3** | 实验确认 | 经实验室高温/光照实验等稳定性指标实测结果反馈 + GC-MS 反打数据校准确认 | 中权重 |
| **L4** | 客户确认 | 完成对外商业寄样并得到正向通过和肯定通知书 | 高权重 |
| **L5** | 商业投产 | 成功获得客户打款、实现工程量产并直接进入销售商品主数据表的闭环成熟配方 | **黄金标准** |

**核心原则**：
- 前端界面上调香师操作的具体交互过程日志**绝对不允许作为未经甄别的反馈特征直接自动向模型喂送**
- 真正获准被视为具有高学习价值的反馈输入，被严格框定在 L2-L5 四级内
- 正确流程为：**实时记录 → 后续结果验证 → 筛选高质量案例 → 定期训练或更新规律 → 独立测试集验证后上线**

# 四、AI 边界评估：哪些功能需要 AI、统计学或传统工程

## 分类原则

**【结论】** 系统整体必须有 AI，但绝不是每个功能都由大模型完成。真正合理的架构是四类能力配合：确定性计算与规则引擎、统计学习与优化算法、大语言模型、AI 工程代理。

大模型通过 Function Calling 调用专业模块，通过 Structured Outputs 将自然语言转成符合 JSON Schema 的结构化参数；精确计算仍由代码和数据库完成。

## A 类：没有大语言模型就很难成立

| 功能 | AI 的作用 |
|------|-----------|
| 客户 Brief 解析 | 把自然语言拆成产品概念、目标用户、香气要求、硬约束和软目标 |
| 2.0 产品概念 → 香气故事 | 完成语言与嗅觉表达之间的转译 |
| 香气故事 → 感官结构/三调表 | 把抽象叙事转为韵、象形和香气结构 |
| 概念匹配诊断（2-06） | 判断配方表达的语义是否吻合品牌和产品概念 |
| 自然语言反馈理解 | 把"太粉、尾部闷、不够鲜活"等反馈转成结构化调香任务 |
| 任务编排（L3） | 判断应该调用哪些模块（平衡/协调/细致/成本/稳定性……） |
| 结果解释（X-07） | 用调香师可理解的语言解释为何这样改方 |
| 历史案例语义检索（X-05） | 从大量修改记录中找出"问题相似但措辞不同"的案例 |

**A 类功能中大模型的职责**：把人的语言转成软件模块能执行的结构化任务，再把模块结果翻译回人的语言——而非直接计算配方。

## B 类：需要学习算法，但不一定需要大语言模型

| 功能 | 最适合的技术 | 大模型是否必需 |
|------|-------------|---------------|
| 原料共现权重 | 统计、条件概率、共现矩阵、图算法 | **不必** |
| Performer 搭配关系 | 图模型、加权关联、历史配方分析 | **不必** |
| Performer/Mediator 与 Modifier 匹配 | 案例检索、排序模型、图学习 | 不必，但可辅助解释 |
| 配方相似度 | 特征工程、距离函数、机器学习排序 | **不必** |
| 稳定性风险预测 | 监督学习、相似案例、分类模型 | **不必** |
| 感官一致性预测 | 统计模型、异常检测 | **不必** |
| 配方角色识别 | OAV 规则 + 历史学习模型 | **不必** |
| 细致度候选生成 | 案例检索 + 候选排序 + 生成算法 | AI 有价值 |
| Fine fragrance → Consumer 转换 | 案例学习 + 品类模型 + 约束优化 | AI 有价值 |
| Version 0 排序 | 检索、特征评分、学习排序 | AI 有价值 |

**核心警告**：原料关系权重**不能让大模型"读几万条配方后凭感觉总结"**。正确做法是用程序对全部历史配方进行精确计算（共现频率、条件概率、PMI、控制品类/角色/数量级后的关联强度、成功/失败配方差异等）。大模型可以解释结果、决定调用哪个分析，但不代替这些精确计算。

## C 类：主要是数学优化和确定性规则，不需要 AI

| 功能 | 主要实现方式 |
|------|-------------|
| OAV 计算 | 普通程序（公式 C/T） |
| 原料角色初步判断 | 规则引擎（基于 OAV 区间） |
| 配方成本计算 | 普通程序（单价 × 用量） |
| 不同价格 Cap 下求解 | 线性/非线性/整数约束优化 |
| 法规合规检查 | 版本化规则库 |
| 禁限用量检查 | 规则 + 数据库 |
| 总量/稀释度/单位换算 | 普通程序 |
| 采购可行性 | 库存和供应链查询 |
| 用户权限和数据隔离 | 身份权限系统 |
| 配方版本管理 | 普通业务系统 |
| 审批/日志/追溯 | 普通业务系统 |

**核心原则**：大模型可以解释"这个候选方案因成本上限 50 元/kg 替换了 A 并牺牲了部分细致度"，但它**不能成为成本、法规和权限判断的最终真相来源**。

# 五、商业载体与执行管理分支

## 1. 双马 vs. 新主体（技术平台公司）的业务边界与授权联动

### 业务开发定位对比

| 维度 | 双马（现有香料公司） | 新平台公司（独立技术主体） |
|------|---------------------|--------------------------|
| **核心职能** | 香料研发、生产、销售业务 | 以 AI 赋能的平台模式，支撑全球独立调香师创新及产品化 |
| **开发内容** | 直接服务于双马内部业务流程增效的功能 | 可对外输出、可独立作为 SaaS 功能模块的核心算法与工具 |
| **目标用户** | 双马内部调香师、销售、品香人员 | 外部独立调香师、合作品牌、行业客户 |
| **数据主权** | 双马专属数据域 | 平台公共能力域 + 租户私有数据域 |

### 双向功能流动

- **平台 → 双马**：平台公司开发的独立功能模块，可反售给双马，嵌入双马研发中台使用
- **双马 → 平台**：双马将原料数据库、配方数据库、产品数据库的**使用权**授权给平台公司进行新功能开发

### 数据三层切分

#### 第 1 层：双马专属数据域（平台公司不可默认读取）

- 客户 Brief 和客户名单
- 所有客户配方
- 寄样、报价、成交、销售数据
- 双马调香师的工作轨迹
- 双马原料采购与成本
- 未获授权的历史成功案例

#### 第 2 层：平台公共能力域

- 公共原料知识（理化性质、阈值、法规等）
- 通用法规和理化性质数据库
- 通用算法和模型
- **不含双马客户秘密**的原料关系模型
- 平台工具和功能模块
- 已获授权且完成匿名化的经验数据

#### 第 3 层：租户私有数据域（外部调香师/品牌）

- 每个租户只能看到自己的 Brief、配方
- 无法查看双马或其他调香师的数据
- 是否允许用其反馈改善公共模型，需**单独授权**

### 跨中台联动接口建议（R27/R28 遗留设计项）

以下为基于讨论提炼的架构接口建议，属于待最终落地设计确认的方向：

1. **双马中台 ↔ 平台智能服务的 API 网关**：通过 Formulation Intelligence Service 的标准化 API 调用，实现功能模块的热插拔
2. **主数据授权与同步机制**：双马授权特定原料/配方/产品数据子集给平台，平台在授权范围内进行模型训练和功能开发
3. **功能模块的灰度发布通道**：平台新开发的模块先在双马内部试用验证，通过后上架平台 SaaS
4. **结算与授权管理**：每个功能模块对双马和外部租户的授权、计费和版本管理独立可控

*(演进与纠偏原因：R27 中用户提出"双马开发 vs 平台开发"的区分问题，以及"平台开发的功能反售给双马"的双向流动模式。此处的接口建议为基于讨论方向的推论，尚未经用户逐条确认，属于待推进的设计议题。)*

## 2. 人员组织与团队配置

### 【终局结论】3+1 核心配置

不应只招聘一个"很会使用 AI 的年轻人"——这样容易产生大量 Demo 却没有稳定的架构、数据治理和可上线算法。真正缺的是三个不同能力：架构职能、AI 应用职能、数据算法职能。

### 核心团队

#### 1. 现有双马工程师：双马系统与数据接口负责人

**职责**：现有研发中台维护、数据库和字段管理、双马内部权限、与中台供应商对接、新旧系统接口、内部部署和运维
**KPI**：保证双马数据和业务流程能够可靠接入，而非研究调香算法

#### 2. 新招——平台技术负责人 / 架构型全栈工程师（第一优先级）

**背景要求**：
- 真实平台或 SaaS 系统架构经验
- 熟悉 API、数据库、权限、多租户和云部署
- 能写后端及必要的前端
- 能设计日志、测试、监控、备份
- 能审查供应商和 AI 生成代码
- 能与业务负责人将抽象工作流程转成系统
- 最好做过 AI 应用集成，但不要求是模型研究员
- **不能是只做咨询、不写代码的传统架构师**

**负责解决的关键问题**：双马中台与平台公司关系、API 和微服务边界、单租户 vs 多租户、数据权限、外部调香师可见范围、核心算法代码归属、模型调用和日志审计、供应商更换兼容性、数据备份/迁移/删除

#### 3. 新招——AI 应用工程师 / Agent Engineer

**背景要求**：
- Python，最好同时掌握 TypeScript
- 熟悉大模型 API、Tool/Function Calling、Structured Outputs
- RAG、向量检索和案例库
- Agent 工作流
- Prompt 与上下文工程
- Evals、日志和模型效果测试
- 能快速做出可试用原型
- 会使用 AI 编程代理开发

**负责**：Brief 解析、调香对话界面、反馈结构化、任务编排、2.0 语义链路、历史案例检索、大模型与专业模块连接

#### 4. 新招或合作——数据与配方算法工程师

**背景要求**：
- Python、SQL
- 统计学和机器学习
- 图数据与关系计算
- 运筹学或数值优化
- 特征工程与排序模型
- 能处理几万张配方的数据
- 化学信息学/配方/材料/食品/药物研发背景加分（不要求一开始就懂调香）

**负责**：原料关系权重、共现图谱、相似度、稳定性预测、角色模型、约束优化、候选配方生成和排序、训练数据和评估集

### 预算紧张时的最低配置

> **平台技术负责人 + AI/数据复合型算法工程师**（界面和常规接入继续交给现有工程师与供应商）

但从长期看，AI 应用和配方算法最好拆成两个岗位——一个偏语言/交互/Agent，另一个偏统计/数学/优化，很难有人同时做深。

### 暂不全职招聘的职能（年底前采用兼职/顾问/供应商）

数据安全与网络安全顾问、法律/数据权属/知识产权顾问、DevOps/MLOps、专业测试工程师、UI/UX、前端开发、云资源和安全审计

# 六、半年 MVP 落地推演（2026 年 7 月—12 月）

## 年底目标定义

到 2026 年年底做出一个**已经嵌入中台、可供内部调香师试用并持续收集反馈的第一版**是可行的。在半年内把 0.0—2.0 的所有能力都做成熟则不现实。年底目标应是一个范围明确的 MVP，而非"数字调香师全部完成"。

## 开发优先级 A/B/C 矩阵

### A 类：必须上线并真实使用

| 模块 | 内容 |
|------|------|
| 配方标准化（X-01） | 统一全部配方数据的表达格式 |
| OAV 和角色分析（X-02） | 每种原料的浓度/阈值/OAV/角色/香韵贡献 |
| 成本、法规和稳定性检查（0-01, 0-02, 0-05） | 硬约束自动化 |
| Version 0 香精库检索（1.5-01） | Brief → 匹配现成配方 |
| 平衡诊断（1-04 诊断部分） | 判断原料和香韵是否在合理感官位置 |
| 协调诊断（1-05 诊断部分） | 判断韵与韵是否搭配 |
| 成本约束优化（1-10） | 不同价格 cap 下的候选解 |
| 配方版本和反馈闭环 | 中台交互层的版本管理 |

### B 类：形成可试用的自动改方功能

| 模块 | 内容 |
|------|------|
| 平衡优化（1-04 优化部分） | 自动调整 OAV 分布 |
| 协调优化（1-05 优化部分） | 自动改善韵间搭配 |
| 细致度优化（1-06） | 自动增加细节层次 |
| 指定香韵增强（1-08） | 定向提升特定香气方向 |
| Fine fragrance → Consumer 转换（1.5-03, 1.5-04） | 品类适配 |

### C 类：形成可验证原型

| 模块 | 内容 |
|------|------|
| 产品故事到香气故事（2-02, 2-03） | 语言 → 气味叙事 |
| 香气故事到三调表（2-04） | 叙事 → 感官结构 |
| 三调表到 Version 0（2-05） | 感官结构 → 初始配方 |
| Benchmark 自动重构（1-01） | GC-MS → Version 0 |
| 完整 2.0 自动生成链路 | 从品牌概念到配方的端到端 |

## 逐月推演

### 7 月：定义和盘点
- 完整业务功能地图、模块优先级
- 现有中台架构图和数据库盘点
- 统一的模块输入输出协议
- 年底 MVP 范围锁定
- 第一批历史案例集整理
- 决定哪些模块第一批进入开发
- 对现有工程师能力盘点，决定是否招聘平台技术负责人

### 8 月：数据准备和离线原型
- 优先完成：原料 OAV 和角色计算、不同数量级的原料标签结构、原料共现和关系权重计算、Version 0→最终配方的成对案例结构
- 1-2 个模块的离线原型（不接中台，独立验证）
- 技术负责人到位：建立平台代码仓库、开发/测试/生产环境、API/权限/日志标准
- AI 编程工具进入日常开发流程

### 8—9 月：AI 工程师和数据算法工程师到位
- 先做共享底座：配方标准化（X-01）、OAV 与角色引擎（X-02）、原料关系计算（X-04）、历史案例库（X-05）、人反馈结构化、模块调用接口

### 9 月：第一批模块验证（≤ 3 个核心模块）
- 建议组合：**Version 0 检索推荐 + 配方基础诊断（成本/法规/OAV/角色） + 一个真正的自动优化模块**
- 第三个模块在"协调""细致""降本"中选数据和案例最充分的一个
- 产出诊断结果、修改策略、候选配方、修改依据、专家评价结果

### 10 月：接入中台
- 算法服务 API、中台调用接口、配方版本管理、修改前后对比、反馈录入、任务日志、用户权限、测试环境联调

### 11 月：内部调香师试用
- 选择少量真实项目和少量调香师（不全面推广）
- 重点记录：系统建议是否被采用、人修改了什么、系统错在哪里、每个任务节省多少时间、候选配方是否值得打样、调香师是否理解和信任诊断依据、最终客户是否接受

### 12 月：修订和有限推广
- 年底合理状态：中台里存在可调用的 AI 调香入口、可从 Brief 推荐 Version 0、可对现有配方完成基础诊断、至少一个核心优化模块能直接生成候选新配方、人的反馈能被结构化记录、内部部分调香师已在真实项目中使用、已形成下一阶段扩展其他模块的数据和工程基础

## 最大风险控制

1. **同时展开太多功能**：第一版选 2-3 个模块做完整闭环（诊断准确 → 建议合理 → 能生成配方 → 人能反馈 → 经验能保存），而非每个模块都做成半成品
2. **供应商先写界面而模块定义未稳定**：正确顺序是 业务定义 → 离线原型 → 专业验证 → API 标准化 → 中台接入
3. **核心算法写死在供应商代码里**：核心算法应成为独立服务（Formulation Intelligence Service），中台通过 API 调用
